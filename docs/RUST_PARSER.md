# Rust backend

The Rust backend turns a `.lig` grammar into one Rust source file with a lexer and an LR(1)
parser. It reuses the tables the Lean backends build: the Pager `Tables` for the parser, and
`DFA.build?WithVecs`, `DFA.flatOfDFA` and `ByteDFA.byteOfFlat` for the lexer. Nothing is
recomputed in Rust. The loops that are the same for every grammar are in a Rust crate,
`rust/lpg-kernel`, that the generated file calls with its tables. With
`%option gen_rust_verif`, the generator also writes a Lean package that proves the generated
lexer and parser equal to the generated Lean ones, using Charon and Aeneas.

This page says how to run the generator, what the generated file contains and how to call it,
what is proved and what it assumes, and what is missing ("Remaining gaps"). The decisions
behind the design are in the table at the end, numbered D1 to D31; other sections refer to
them.

The emitters are `LeanParserGenerator/Emit/CodegenRust.lean` (parser and assembly),
`Emit/Rust/Lexer.lean` (lexer), `Emit/Rust/Values.lean` (Rust actions),
`Emit/Rust/Bridge.lean` and `Emit/Rust/BridgeIO.lean` (proof package). The proofs that do not
depend on the grammar are in `rust/verif`.

Status: prototype. `parse` returns a trace of the parse (which tokens were shifted and which
productions were reduced), not an AST. With Rust actions in the `.lig` the file also has
`parse_values`, which returns the value of the start symbol. The proofs cover `lex` and `parse`;
they do not cover `tokenize`, `parse_values` or the user's Rust code.

## Running it

Build the generator and run it on the Cedar grammar:
```
lake build leanparsergenerator
.lake/build/bin/leanparsergenerator --backend rust test/cedar/cedar.lig /tmp/cedar.rs
```
`--backend rust <grammar.lig> <out.rs>` writes a single file where it is told. A `.lig` can
instead name its Rust file in its directives, before `%%`:
```
%option gen_rust rust/src/generated.rs
```
The path is relative to the directory of the `.lig` and starts with a name, not with `.` or
`/`. With the option, `leanparsergenerator grammar.lig` (what `lake build parsers` runs for
the fixtures) writes the Rust file next to the Lean modules, creating directories as needed,
and prints `wrote …/generated.rs (Rust)`. To have the build regenerate it when stale, list it
in the `outputs` of the grammar's entry in `genTargets` in `lakefile.lean`. The Lean modules
are unaffected: the `.lig` is parsed once, and the Lean backends ignore the Rust-only parts.

The first lines of the generated file say which `.lig` it came from:
```
// Generated by LeanParserGenerator from a .lig grammar. DO NOT EDIT.
// Source: test/cedar/cedar.lig
```

Where the files of a grammar are named, for `cedar.lig`:

| File | Named by |
|---|---|
| `CedarVerified.lean`, `CedarParser.lean`, `CedarLexer.lean`, `CedarLexerRoundtrip.lean`, `CedarParserRoundtrip.lean` | the `.lig` file name and its `%option`s, next to the `.lig` |
| `rust/src/generated.rs` | `%option gen_rust` |
| `rust/src/hooks.rs` | `rust … => crate::hooks::…` lines in the `%lexer` block; the file is handwritten |
| `rust_bridge/` | `%option gen_rust_verif` |

Then, from the crate in `test/cedar/rust`:
```
cd test/cedar/rust
cargo build --release
./target/release/tree policy.cedar                    # the parse tree as an outline
./target/release/check policy.cedar                   # ok, lex, or parse <token> <state> <lookahead>
./target/release/cedar-rust-parser a.cedar b.cedar    # benchmark over files
```

## The generated file

All items are in the one file, which is included as a module (`mod generated;` or
`pub mod generated;`). The crate needs the kernel as a dependency; in this repository it is a
path dependency:
```
[dependencies]
lpg_kernel = { path = "path/to/lpg-kernel" }
```

Common items:

- `EOF: u16`, the terminal index of the end-of-input token.
- `struct Token { rule: u16, term: u16, start: u32, end: u32 }`: the lexer rule that matched,
  its terminal index and its byte span. It has no value (see `token_value`) and is 12 bytes.
  Re-exported from `lpg_kernel`, with `Node`, `Entry`, `ParseError` and `PROD_FLAG`.
- `mod term`, one `u16` constant per `%token`, named like the token.
- `NUM_TERMINALS`, `NUM_NONTERMINALS`, `NUM_PRODUCTIONS`, `NUM_STATES`.
- `term_name(t: u16)`, `nonterm_name(n: usize)`, `prod_lhs(p: usize)`, `prod_len(p: usize)`:
  names and shapes, for printing and for rebuilding the tree.

From the lexer, if the grammar has a `%lexer` block:

- `enum Tok<'a>`, one variant per `%token`, with a payload for the tokens that carry a value
  ("Token types" below). It derives `Clone`, `Debug`, `PartialEq` and `Eq`, and `term()` is the
  terminal index.
- `fn tokenize(src: &str, out: &mut Vec<Token>) -> Result<(), LexError>`.
- `fn lex(src: &[u8], out: &mut Vec<Token>) -> Result<(), lpg_kernel::LexFail>`, for a lexer
  with one mode: `lpg_kernel::lex` on this grammar's tables. `tokenize` calls it and then fills
  in the terminals of `g s` rules. Callers use `tokenize`; `lex` is what the proofs are about.
- `fn token_value(rule: u16, text: &str) -> Option<Tok>`: the `Tok`, with its value, that the
  lexer action of `rule` builds from the lexeme `text`. `EOF_RULE` is the `rule` of the
  end-of-input token.
- `struct LexError { pos, byte_pos, ch, reason }` and `enum LexErrorReason`.
- `mod lexrt`, the Rust versions of the library functions that lexer actions may call.

From the parser:

- `fn parse(tokens: &[Token], stack: &mut Vec<Entry>, nodes: &mut Vec<Node>) ->
  Result<(), ParseError>`: `lpg_kernel::parse` applied to the grammar's tables (D26).
- `struct Node { kind: u16, start: u32, end: u32 }`, `const PROD_FLAG: u16 = 0x8000`.
- `struct Entry`, the parse stack cell, public so the caller can own the buffer.
- `struct ParseError { token: usize, state: usize, term: u16 }`.
- With Rust actions: `parse_values` and `Stacks` ("Rust actions" below).

A grammar without a `%lexer` block gets only the parser and the terminal constants. There is no
`Tok`, `tokenize`, `token_value` or `lexrt`, and the caller builds the `Token`s ("Grammars
without a lexer" below).

## Calling it

From `test/cedar/rust/src/lib.rs`:
```rust
pub mod generated;
pub mod hooks;     // the handwritten functions named in the %lexer block

use generated::{Entry, LexError, Node, ParseError, Token};

#[derive(Default)]
pub struct Parser {
    pub stack: Vec<Entry>,
    pub nodes: Vec<Node>,
}

impl Parser {
    pub fn parse(&mut self, src: &str, tokens: &mut Vec<Token>) -> Result<(), Error> {
        tokens.clear();
        generated::tokenize(src, tokens).map_err(Error::Lex)?;
        generated::parse(tokens, &mut self.stack, &mut self.nodes).map_err(Error::Parse)
    }
}
```
The numbers in "Performance" are for `opt-level = 3`, `lto = true`, `codegen-units = 1`.

`tokenize` appends to `out` and does not clear it. The last token it appends is the `%eof`
token. `parse` clears `stack` and `nodes` first, so the buffers can be kept between calls;
fresh buffers per call cost about 2 µs on Cedar. If `tokens` has no end-of-input token, `parse`
supplies one.

### The parse trace

On success `nodes` holds the tree in postorder: one node per shifted token, one per reduction.
The last node is the augmented start production `S' → S $`. A node's `kind` is either a
terminal index (a token) or `PROD_FLAG | p` for production `p`. `start` and `end` are byte
offsets; a node for an empty production has `start == end` (not `0..0` as in the Lean parsers,
see "Spans" below). The trace does less work per reduction than the Lean parsers, which build
the AST, and it is what the parser theorem talks about.

To rebuild the tree, scan `nodes` with a stack: push a leaf for a token node, and for a
production node pop `prod_len(p)` subtrees and make them its children. `src/bin/tree.rs` in the
Cedar crate does this:
```rust
fn build(nodes: &[Node]) -> Vec<Tree> {
    let mut stack: Vec<Tree> = Vec::new();
    for &node in nodes {
        let children = if node.kind & PROD_FLAG != 0 {
            let n = prod_len((node.kind & !PROD_FLAG) as usize);
            stack.split_off(stack.len() - n)
        } else {
            Vec::new()
        };
        stack.push(Tree { node, children });
    }
    stack
}
```
For `permit(principal, action, resource) when { 1 + 2 };` the tree starts
```
S' [0..52]
  policies [0..51]
    list_policy [0..51]
      policy [0..51]
        list_annotation [0..0]
        any_ident [0..6]
          common_ident [0..6]
            PERMIT "permit"
        LPAREN "("
        …
```
Productions come from the grammar after macro expansion, so `list_policy` is the expansion of
`list(policy)`.

### Parser tables and errors

`ACTION[state][t]` is 0 for error, `(target << 1) | 1` for shift and `(prod + 1) << 1` for
reduce. `GOTO`, `DEFAULT_REDUCE`, `LHS` and `RHS_LEN` are the Lean tables. Tables are 2D, all
`u16`, with one `const` per row (D28). The loop follows `Runtime.Exec.step`: use the default
reduction if the state has one, otherwise look up the action. A reduction with no goto is
accepted, as in `Exec.reduce`; with the generator's tables only the augmented production has
none (D30). The `%eof` token is the augmented `$`, as in `Emit.emitDecoder`. The kernel's
`parse` takes a step budget, `lpg_kernel::FUEL` (2^62).

`ParseError`:

- `token`: the index in `tokens` of the offending token.
- `state`: the LR state; `term`: the terminal index of the lookahead.
- `term == u16::MAX` is an internal inconsistency (a stack underflow, or a reduction with no
  goto that is not the augmented production). The tables come from a Pager construction that the
  Lean side validates, so this is not expected. `TERM_OUT_OF_FUEL` (65534) means the step budget
  ran out.

`term_name(term)` gives the lookahead's name. The set of terminals the state would have
accepted is not exposed; the Lean parser's `diagnose` computes it.

## Rust actions

The semantic actions of a `.lig` are Lean terms, and the Rust backend does not translate them.
Instead the grammar author writes a Rust action after each Lean one, between `!!rust{` and `}`,
and a Rust type after each rule's Lean type:
```
expr :: Expr !!rust{crate::ast::Expr<'a>}
  | e=expr PLUS t=term { Expr.add e t }
                       !!rust{ crate::ast::Expr::Add(Box::new(e), Box::new(t)) }
  | t=term             { t }
                       !!rust{ t }
```
`test/rustactions/rustactions.lig` is a complete example, with its Rust AST in
`test/rustactions/rust/src/ast.rs`.

The generator pastes each Rust action, unchanged, into the reduction of its production, as the
body of a block that must evaluate to the rule's Rust type (D17). It never reads the text, so any
Rust works: statements before the final expression, calls into the user's modules, closures. It
uses the Rust type of each rule only to decide which stack the rule's values live on. A rustc
error is reported in `generated.rs`, and each arm carries a comment with the rule name and
alternative number. The Lean side is unchanged, so the Rust side is free to use another
representation: `Box`, an arena, borrowed strings, a `VecDeque` for a right-recursive list.

The reason for this split is that the parsing theorems are stated on parse trees. The proof that
the Rust parser corresponds to the Lean one needs the two parsers to agree on the trace, and does
not need their values to agree. The Lean and the Rust action of a production are separate
pieces of code, and nothing checks that they build the same thing.

What is in scope in the body:

- Each binder `x` of the alternative is a local `x` with the type of its symbol: the Rust type
  after `!!rust` on the rule head for a nonterminal, and the lexer's payload type for a token
  (`&'a str` for `String`, `u64` for `Nat`, `i64` for `Int`, `bool`, `char`; `()` for a token
  without a payload). The value is moved in.
- `x_span` is a `generated::Span { start: u32, end: u32 }`, the byte range of the symbol. It is
  bound for every binder; the function allows `unused_variables`.
- `'a` is the lifetime of the source text, defined when some token has a `String` payload or a
  type mentions `'a`.
- A binder that is a Rust keyword is bound as `r#name`.
- The generated code uses names that start with `__`.
- Types are written as seen from `generated.rs`: the user's module is `crate::ast::…`.

Rules:

- All or nothing (D19). If any rule has a Rust type or any alternative a Rust action, all of
  them need one; missing ones are listed. A reduction `{ x }` of a single symbol with the same
  Rust type as its rule generates no code (D22).
- Rules created by macros (`list(X)`, `nonempty_list(X)`, `option(X)`, `separated_list(sep, X)`,
  `separated_nonempty_list(sep, X)`) get Rust text from the generator (D21). A list is a
  `std::collections::VecDeque<T>` (the expansion is right-recursive, `x :: xs`, and `push_front`
  is O(1)) and an option is `Option<T>`, where `T` is the Rust type of the element: the
  `!!rust{type}` of the rule it names, the payload type of a token, or the type of a nested
  macro. A user who wants another representation writes the list rule by hand.
- A grammar without a `%lexer` block can have Rust actions only if no token has a payload, since
  there is no source text to rebuild a value from.
- A `}` in a Rust string or comment must be balanced, since the frontend finds the end of the
  action by counting braces. The bootstrap lexer keeps the Rust text inside the type or action
  token and `assembleSurface` splits it off, so `lig.lig` is unchanged (D20).

Calling it:
```rust
let mut toks = Vec::new();
tokenize(&src, &mut toks)?;
let mut stacks = Stacks::new();                 // keep it between calls
let program = parse_values(&src, &toks, &mut stacks)?;
```
`parse_values(src, tokens, stacks)` returns `Result<T, ParseError>`, `T` the Rust type of the
start rule. The source text is what the value of each shifted token is rebuilt from, with
`token_value` (D27); a hook that picks the terminal runs again there. `Stacks` holds the entry
stack of states and spans and one `Vec` per distinct Rust type (D18); `parse_values` clears them
first. A reduction pops the values of its right-hand side, each from the stack of its type, binds
them, evaluates the Rust body and pushes the result on the stack of the rule's type. A token's
payload is pushed when the token is shifted.

`parse_values` is the same LR loop as `parse`, generated from its own template; it does not call
the kernel. The two read the same tables, and `test/rustactions/rust/src/main.rs` checks on its
samples that they accept the same token lists and fail at the same token, state and lookahead.

The cost of an action is the cost of moving its arguments and its result between stacks. If an
AST node is several hundred bytes, put its large fields behind a `Box`, or allocate nodes in an
arena and make the rule's type a reference or an index.

### Allocating from an arena

Each `Box` and each `VecDeque` of an AST is a call to the allocator, one or two per token on a
grammar with a deep AST, and freeing the tree costs the same again. Two options connect an arena
to the actions (D23):
```
%option rust_ctx  crate::ast::Arena
%option rust_list crate::ast::lists
```
`rust_ctx T` adds a parameter `ctx: &'a T` to `parse_values`, visible in every Rust action. `T`
is the user's; with `bumpalo`, `pub type Arena = bumpalo::Bump;` and `ctx.alloc(x)` replace
`Box::new(x)`. Nodes are then `&'a X` fields, and the AST needs no destructor.

`rust_list P` makes the macro rules build `P::List<'a, T>` with `P::nil(ctx)`, `P::one(ctx, x)`
and `P::cons(ctx, x, xs)` instead of a `VecDeque<T>`. It needs `rust_ctx`. A list of arena cells
is enough, since the expansion only conses. `test/rustactions/rust/src/arena.rs` is a complete
one and `test/rustactions/rustarena.lig` the grammar of `rustactions.lig` using it.

The values borrow from `ctx`, so a `Stacks` is tied to one arena. To keep the buffers across
parses with a new or reset arena, `stacks.recycle()` empties the stacks and returns them with a
new lifetime (D24). It is a `transmute` of empty vectors and the only `unsafe` in the generated
parser. It is generated only with `rust_ctx`.
```rust
let mut stacks: Stacks<'static> = Stacks::new();
let mut arena = Arena::new();
loop {
    arena.reset();
    let mut st = stacks.recycle();
    let ast = parse_values(&toks, &mut st, &arena)?;
    /* use ast; it ends before the next reset */
    stacks = st.recycle();
}
```

## Lexers

### Actions

The Lean backends accept any Lean term as a lexer action. The Rust backend accepts five forms,
so that no Lean has to be translated (D14). With `s` the `as` binder:

| Action | Meaning | Rust |
|---|---|---|
| `skip` | no token | |
| `Tok.IDENT` | a token without a value | `Tok::IDENT` |
| `Tok.NAME s` | the value is the lexeme; `NAME` carries `String` | `Tok::NAME(text)`, `text: &'a str` |
| `Tok.NAME (f s)` or `Tok.NAME s.f` | the value is `f` of the lexeme | `Tok::NAME(v)` for `Some(v) = f(text)` |
| `g s` | the token is `g` of the lexeme | the token `t` for `Some(t) = g(text)` |

Anything else is rejected, with the mode and rule number in the message. A composition such as
`(s.replace "_" "").toNat!` is rejected; it has to be one function.

`f` and `g` are Lean functions, and each needs a Rust counterpart. These are built in, in the
generated `lexrt` module:

| Lean | Rust |
|---|---|
| `String.toNat!` | `lexrt::to_nat(&str) -> Option<u64>` |
| `String.toInt!` | `lexrt::to_int(&str) -> Option<i64>` |
| `String.length` | `lexrt::length(&str) -> Option<u64>` |

Any other function needs a line in the `%lexer` block, before the rules, naming a Rust function
the user writes. From `cedar.lig`:
```
%lexer {
  let identStart = ['a'-'z' 'A'-'Z' '_']
  …
  rust keywordOrIdentifier => crate::hooks::keyword_or_identifier
  rust stripStringQuotes   => crate::hooks::strip_string_quotes

  | identStart identCont* as value => { keywordOrIdentifier value }
  | "\"" … "\"" as value           => { Tok.STRINGLIT (stripStringQuotes value) }
  …
}
```
and in `test/cedar/rust/src/hooks.rs`:
```rust
use crate::generated::Tok;

pub fn keyword_or_identifier(text: &str) -> Option<Tok<'_>> {
    Some(match text {
        "permit" => Tok::PERMIT,
        "forbid" => Tok::FORBID,
        …
        _ => Tok::IDENTIFIER(text),
    })
}

pub fn strip_string_quotes(text: &str) -> Option<&str> {
    let mut cs = text.chars();
    cs.next();
    cs.next_back();
    Some(cs.as_str())
}
```
The signatures are fixed: `fn f(&str) -> Option<R>` for `Tok.NAME (f s)`, with `R` the Rust
type of the value `NAME` carries, and `fn g(&str) -> Option<Tok<'_>>` for `g s`. `None` means
the Lean result does not fit the Rust type; the lexer then fails at the start of the lexeme with
`Unrepresentable` (D15). The generated code calls the path as written, so a missing-function
error from rustc means the path does not match the module.

The Lean definition stays in the `%lexerheader` and is the specification. Nothing checks that
the Rust function agrees with it (see "Remaining gaps"). Where the types differ, the Rust one
has fewer constraints: Cedar's `IDENTIFIER` carries `{s // s ∉ keywords}` in Lean and a plain
`&str` in Rust. The Lean lexer generator does not read the `rust` lines or restrict actions.

Keywords do not need a function. The lexer takes the longest match and breaks ties by rule
order, so listing the keywords as rules before the identifier rule gives the same tokens with
no Rust code. On Cedar that form produced identical token kinds and spans.

The `eof` action, if there is one, must be the constant `Tok.<the %eof token>`.

### Token types

A token with a value takes the Rust type of its declared Lean type (D7, D13):

| Lean type | Rust type |
|---|---|
| `String` | `&'a str`, a slice of the source |
| `Nat` | `u64` |
| `Int` | `i64` |
| `Bool` | `bool` |
| `Char` | `char` |
| `{ x : T // p }` | the Rust type of `T` (the predicate is dropped) |

Any other type is an error naming the type. `Tok<'a>` has a lifetime parameter only if some
token has a `String` payload.

A lexed `Token` carries no value, so it has no lifetime. `rule` numbers the lexer rules of all
modes in order, and `token_value(rule, text)` rebuilds the `Tok` from the source text of the span
(D27).

### Tables and the loop

The byte DFA from `ByteDFA.byteOfFlat` has 256 columns per state. The emitter merges bytes whose
columns agree in every state into classes (Cedar: 53 classes, 71 states). The states are
renumbered with the accepting ones last, and row 0 is the dead state. Before writing the tables
the generator checks them against the byte DFA for every state and byte (D16).

A lexer with one mode is `lpg_kernel::lex` with the tables `LEX_CLASS` (byte to class),
`LEX_TRANS[state][class]` (the next state, 0 for dead, one constant per row), `LEX_ACCEPT[state]`
(the rule plus one), `RULE_TERM[rule]` (the terminal, `TERM_SKIP` for a rule that emits nothing,
`TERM_HOOK` for one whose terminal a function computes), `LEX_START` and `LEX_ACCEPT_FROM` (the
accepting states are those from it on) (D29). The loop is the usual longest match: run until the
dead state, remember the last accept, fail if no rule matched or the match is empty. A tie goes
to the earlier rule, as in Lean. A state that steps to itself starts a separate inner loop over
the run (identifier characters, spaces), whose loads do not depend on each other. The `%eof`
token is appended last. An input longer than `u32::MAX` bytes is an error (`TooLong`): the spans
would not fit.

`tokenize` calls `lex`, then makes one pass over the tokens for the rules with a function: a
`g s` rule gets its terminal from `g`, and a `Tok.NAME (f s)` rule fails with `Unrepresentable`
where `f` returns `None`. The first error in the source is reported, as when the functions ran
inside the loop. Running the functions after the loop keeps closures out of the kernel.

### Modes

`rule name { … }` blocks with `enter m` (push) and `leave` (pop) work as in
`Lexer.tokenizeByteAux`: a stack of modes starting with the first, and end of input is an error
unless exactly one mode is on the stack. A lexer with several modes does not use the kernel. It
keeps its own loop in the generated file, with per-mode tables `M<i>_CLASS`, `M<i>_TRANS` and
`M<i>_ACCEPT` in which a state is the offset `(k + 1) * classes` of its row. This loop is not
proved, and no public fixture uses modes.

### Errors and differences from the Lean lexer

`LexError` has `pos`, a character offset as in Lean's `LexError.pos`; `byte_pos`, the same
position in bytes; `ch`, the offending character (`None` at end of input); and `reason`:
`NoMatch` (no rule matches), `Unrepresentable` (a rule matches but its value does not fit the
Rust type), `EndInMode` (end of input inside a nested mode) or `TooLong`.

The Rust lexer differs from the Lean one in three places:

- A numeral beyond `u64` (`i64` for `Int`) is a lexer error in Rust; Lean accepts it with an
  unbounded `Nat`. `18446744073709551615` lexes identically; `99999999999999999999999` fails at
  its first character. The Rust lexer never returns a wrong value. Cedar assumes its numerals
  fit `u64`.
- `String.toNat!` on a string that is not decimal digits panics and gives 0 in Lean; `to_nat`
  returns `None` and Rust fails. A transform that decodes hex or binary digits has to say so in
  its own definition.
- The Rust lexer always appends the `%eof` token. Without an `eof` clause, Lean's token list has
  none and the parser supplies it, so the parse results agree.

## Grammars without a lexer

C99's fixture has no `%lexer` block, so the file has only the parser. The caller supplies
`Token`s using the constants in `mod term` (`rule` is not read):
```rust
use generated::{parse, term, Token, EOF};

let toks = vec![
    Token { rule: 0, term: term::INT, start: 0, end: 3 },
    Token { rule: 0, term: term::IDENTIFIER, start: 4, end: 5 },
    Token { rule: 0, term: term::SEMICOLON, start: 5, end: 6 },
    Token { rule: 0, term: EOF, start: 6, end: 6 },
];
```
A token whose terminal is out of range is a `ParseError`, not a panic.

## Proving the Rust code equal to the Lean code

### Asking for it

In the `.lig`, next to `gen_rust`:
```
%option gen_rust rust/src/generated.rs
%option gen_rust_verif rust_bridge
```
The directory is relative to the `.lig`, like the Rust path. `gen_rust_verif` needs `gen_rust`.
Then
```
leanparsergenerator cedar.lig
```
writes the Lean modules, the Rust file, and the proof package. In this repository,
`lake build parsers` runs `leanparsergenerator --skip-rust-verif`, which writes everything else
and leaves the package as it is, so that the build does not need Charon and Aeneas (D31).

The proofs cover grammars without a `%lexer` block, and grammars whose lexer has a single mode
and whose rules stay in it (no `enter` or `leave`). For other grammars the generator fails;
with `%option rust_verif_optional` it warns and writes no package, so that a grammar can have
the Rust code without the proof. The check is `coverage` in `Emit/Rust/Bridge.lean`.

### Requirements

On top of what the generator and the Rust crate already need:

- `charon` and `aeneas`, on `PATH` or in `$AENEAS_DIR/charon/bin` and `$AENEAS_DIR/bin`, at the
  revisions `rust/verif/lakefile.lean` pins. Charon builds the crate with its own pinned nightly
  toolchain.
- `cargo`. The crate is the nearest directory above the generated file with a `Cargo.toml`,
  which the user writes. It must depend on `lpg_kernel` (for now by path), and the generated file
  must be a module of the crate (`src/generated.rs` is `crate::generated`). The crate may be a
  library or a binary.
- The generator's `rust/verif` package next to the kernel crate (`<kernel>/../verif`), which
  holds the proofs that do not depend on the grammar. The generated package requires it.

### What is generated

For `cedar.lig` with `gen_rust_verif rust_bridge`, in `test/cedar/rust_bridge`:

| File | What it is |
|---|---|
| `CedarRustBridge/Types.lean`, `Funs.lean` | The Charon and Aeneas translation of the crate, from `crate::generated::parse` and `crate::generated::lex` |
| `CedarRustBridge/TypesExternal.lean`, `FunsExternal.lean` | The kernel the translation calls: `Kernel.Types` and `Kernel.Funs` of `rust/verif` |
| `CedarRustBridge/LexCert.lean` | The certificate of the lexer check: the Rust lexer tables packed into numbers, the Rust state of each state of the Lean DFA, the intervals of code points the check walks |
| `CedarRustBridge/Proof.lean` | The parser theorem |
| `CedarRustBridge/LexProof.lean` | The lexer theorems (only with a `%lexer` block) |
| `CedarRustBridge.lean` | Imports both |
| `lakefile.lean`, `lean-toolchain` | Written once, if absent; edit them freely |

Every other file is rewritten by each run. The checks in the generated files run in the kernel
(`decide +kernel`), so a wrong size or certificate makes the package fail to build; it cannot
produce a wrong theorem.

The lakefile requires `rust/verif` and shares its package directory, so Aeneas and Mathlib are
built once. The generated Lean modules of the grammar (`cedar.CedarParser`, `cedar.CedarLexer`)
must be reachable: in this repository they come from the generator's package, which `rust/verif`
requires. For a grammar in another package, add a `require` of that package to the lakefile.

Building:
```
cd test/cedar/rust_bridge && lake build
```
With `rust/verif` already built, this takes about 30 s for the translation of the Cedar tables
and 40 s for the checks of the package (of which about 12 s for the parser tables in
`Proof.lean` and 16 s for the lexer in `LexProof.lean`).

### The kernel

The proofs about `lpg_kernel::parse` and `lpg_kernel::lex` are in `rust/verif`, about the
translation in `rust/verif/Kernel/{Types,Funs}.lean`. Each run translates the kernel the crate
depends on and fails if the translation is not that one. After a change to the kernel,
```
leanparsergenerator --rust-extract-kernel rust/lpg-kernel rust/verif/Kernel
```
rewrites the translation, and checks that every function Aeneas has no model for is in
`rust/verif/Kernel/FunsExternal.lean`. The proofs in `rust/verif` then have to be updated by
hand.

### The theorems

In namespace `<crate>.Proof` (for Cedar `cedar_rust_parser.Proof`):

- `parse_lean`: for tokens whose terminals are in range and equal to those of a Lean parser
  input, the Rust `parse` ends as the kernel's machine, whose run is `Spec.stepN` for 2^62 steps
  on the tree table of the Lean parser's table (`CedarParser.table`), with the node vector the
  postorder trace of the parse tree, with spans.
- `lex_agrees`: on the UTF-8 bytes of a string, the Rust `lex` and
  `Lexer.tokenize CedarLexer.lexer` report the same run of the Lean DFA (`Spec.ruleRun`),
  including the position of an error.
- `tokens_agree`: for a run without error, the Rust tokens and the Lean tokens are in one-to-one
  order with the same terminals, except for the rules in `hooks` (for Cedar, rule 5), whose
  terminal a Rust function computes.

They use the axioms `propext`, `Classical.choice` and `Quot.sound` only; there is no `sorry`
and no `native_decide` in `rust/verif` or in the generated package. What they assume is under
"Conventions and assumptions"; what is not proved is under "Remaining gaps".

### How the proofs work

Aeneas translates a subset of Rust, so the code to prove is written for it:

- The loops that are the same for every grammar are in `rust/lpg-kernel` and take the tables as
  arguments. The kernel is translated and proved once. A grammar's crate is translated with the
  kernel as an external dependency (`--opaque lpg_kernel`), so the call
  `lpg_kernel::parse(tokens, stack, nodes, &ACTION, …)` in `generated.rs` is checked too, and the
  statement for a grammar is the kernel theorem applied to its tables.
- Tables are `[[u16; N]; S]` with one `const` per row. Aeneas writes an array as one Lean list
  literal, and Lean elaborates one list literal in time superlinear in its length (4000 entries:
  140 s). Rows of `NUM_TERMINALS` elements take about 1 ms per entry (Cedar's 442 rows: 24 s).
- Tokens are plain data (`Token`), with no lifetime and no value (D27). Values are not part of
  what is proved: the correspondence is on the trace and on the tokens' terminals and spans.
- Only the operations of `Vec` and slices that Aeneas models are used, plus `Vec::clear` and
  `Vec::truncate`, whose models in `rust/verif/Kernel/FunsExternal.lean` are trusted.

The parser:

- `Spec.run_eq_eval` (`Spec/Trace.lean`): `Exec.run` on any table and any semantic actions is the
  evaluation of the tree that the same table builds with the action "make a node". The Rust
  trace only has to be compared with that tree.
- `Spec/Machine.lean` is a pure Lean transcription of one iteration of the kernel loop (`mstep`),
  and `Spec/MachineSim.lean` proves that it refines `Exec.step` on the tree table
  (`sim_run_init`).
- `Kernel/ParseBody.lean` proves that the Aeneas translations of `reduce`, `first_start`,
  `lookahead` and the body of `parse` equal the pure machine; the loop theorem follows by
  induction on the fuel. `lpg_kernel.Proof.parse_correct` states the result: for tables that
  satisfy `KWf` and `Spec.MWf`, the final stack and node vector of `parse` are those of
  `Spec.mrunN`, and `Spec.RunSim` relates the end of that run to `Exec`: out of fuel, the same
  rejection, the same internal error, or acceptance of a tree whose postorder trace, with spans,
  is the node vector.
- `Spec/TableAgree.lean`: two tables that agree on the states, terminals, nonterminals and
  productions in range, and that stay in range (`TblWf`), take the same steps (`stepN_sim`).
  `Spec/TableCheck.lean` turns equalities of lists between the Rust rows and the arrays of a Lean
  `FlatTable` into that agreement, also for the compressed Lean tables (`mergeEq`,
  `buildDense_toList`). `Kernel/Tables.lean` (`parse_lean`) adds to `parse_correct` that the run
  is the run of the Lean tree table on the Lean input, with each token index replaced by the
  token's value.
- The generated `Proof.lean` checks the grammar's tables by `decide +kernel` and instantiates
  `parse_lean`. With `Spec.run_eq_eval` and `Spec.run_of_stepN` (`Spec/TableAgree.lean`) this
  becomes a statement about `Exec.run CedarParser.table`, when that run does not time out.

The lexer:

- `Kernel/LexBody.lean` (`lex_spec`): the Aeneas translation of `lpg_kernel::lex` is `Spec.llex`
  (`Spec/Lex.lean`), the longest-match loop over the Rust tables, one byte per step. The inner
  loop over runs of one state is proved to skip what the byte-by-byte scan does
  (`Spec.lscan_run`).
- `Spec/LexSim.lean`: if the Rust DFA simulates a Lean character DFA on UTF-8 (`LexSim`: a map
  from Lean states to Rust states that keeps the accepted rule, such that the bytes of every
  character go where the Lean step goes, through non-accepting states), the Rust scan from a byte
  position is `DFA.scan` on the characters from there (`lscanFrom_sim`). Both `Spec.llex`
  (`llex_rules`) and `Lexer.tokenizeAuxDFA` in one mode (`tokenize_rules`) are then reports of
  one rule-level run, `Spec.ruleRun`: every match with its rule, byte span and text, and the
  position of the error if there is one.
- `Spec/Utf8.lean` and `Spec/LexCheck.lean` decide `LexSim`. `String.utf8EncodeChar` is written
  in base 64 (`encN_eq_bytesOf`), and `walk` follows the Rust DFA over the encodings of all the
  code points of an interval at once, splitting on each digit (`walk_sound`). The check is given
  the map of states and the intervals between the endpoints of the edge classes (on which each
  Lean step is constant, `stepChar_congr_interval`), and compares every walk with the Lean step at
  the first valid code point of the interval. The map of states is `newIdx[s] + 1`: the Lean DFA
  and the byte DFA come from the same `DFA.build?WithVecs`.
- The generator writes the map, the intervals, and the Rust tables packed into numbers into
  `LexCert.lean`. The kernel reads a packed number in one shift; the transitions are one number
  per row, because a shift allocates a number the size of its result. `Kernel/LexTables.lean`
  checks that the packed numbers are the Aeneas arrays (`packCheck`) and proves `lex_run`.
- The check is against the literal `CedarLexer.dfa0`, because `byteOfFlat` (partial) and
  `flatOfDFA` (well-founded recursion) cannot be evaluated in the kernel.
- The generated `LexProof.lean` runs `lexSimCheck` in blocks of 32 Lean states, one theorem each
  (`lexSimCheck_of_parts`). The kernel keeps its reductions until the end of a declaration, so a
  single check over a lexer with a few hundred states ran out of memory.

### Conventions and assumptions

- Fuel. `parse` takes `fuel: usize`; the generated wrapper passes `lpg_kernel::FUEL` (2^62).
  Running out gives `Err` with `term = TERM_OUT_OF_FUEL`. Termination is not proved from the
  tables. `Exec.run` takes `2 ^ logN` steps, and `run_of_stepN` relates the two when `Exec.run`
  does not time out.
- Spans. `Exec` has no spans, so the span convention is a specification of its own
  (`Spec/Spans.lean`, `Tree.ann`): a leaf has the span of its lexer token; the `$` leaf has
  `(prev, prev)`; a reduction ends at the end of the previous token and starts at its first child,
  or at `prev` if it has no children. The Lean parsers give `0..0` to an empty production; the
  Rust parser does not.
- `reduce` returns the `Reduced` enum (`Next`, `Accept`, `Inconsistent`). `Reduced` and
  `LexFail` have no derives, to keep the translation small.
- `System.Platform.numBits = 64`.
- `Vec::clear` and `Vec::truncate` are trusted models.
- The lexer is related to `Lexer.tokenize`, the specification over `List Char`. Its equality
  with the `tokenizeFlatStrPos` the Lean parsers run is the Lean side's
  (`tokenizeFlatStr_eq_tokenize`), which uses the `native_decide` flat-table check. The Rust spans
  are the byte lengths of the characters before and through each match (`Spec.ruleRun`); they are
  not compared with the `String.Pos` spans of `tokenizeFlatStrPos`.
- The input bytes are the UTF-8 encoding of the characters (`bytesOf src = encChars cs`), as Rust
  guarantees for `&str`, and there are at most `u32::MAX` of them (else `TooLong`).
- Charon, Aeneas and rustc are trusted to translate and compile the Rust as written.

## Remaining gaps

What is proved is `lex` and `parse` of a one-mode grammar, each against the corresponding Lean
function, separately. Everything below is not proved, not checked, or not built.

Between the proofs and the functions a user calls:

- There is no theorem that composes the lexer and the parser. `tokens_agree` gives the Rust and
  Lean tokens with the same terminals, and `parse_lean` takes as hypothesis that the Rust
  terminals are those of a Lean input; the step from one to the other is not stated, and it
  needs the terminals of the `g s` rules, which are trusted.
- `parse_lean` is about `Spec.stepN` on `CedarParser.table` for 2^62 steps, not about
  `CedarParser.parse`. The Lean parser runs `Exec.runFast` on `flat` with `logNSteps = 20`. The
  pieces to connect the two exist (`run_eq_eval`, `run_of_stepN`, and `runFast_eq_run` in
  `Runtime/ExecFast.lean`) but no generated theorem states the result, and the Rust parser can
  accept where the Lean one times out.
- `tokenize` is not translated: the post-pass that computes the terminals of `g s` rules and
  reports `Unrepresentable` is outside the proof. The proved function is `lex`, which callers do
  not call directly.
- The link from `Lexer.tokenize` to `tokenizeFlatStrPos`, which the Lean parsers run, is the
  Lean side's and uses `native_decide`. The Rust byte spans are not compared with its
  `String.Pos` spans.
- On acceptance the theorem reports `rest`, the forest below the accepted tree. That `rest = []`
  and that the root is the augmented production follow from properties of `Exec` on the Lean
  side; neither is proved here.
- Empty productions have different spans in Rust and in the Lean parsers (`0..0`).

Code that is generated but not covered by any proof:

- `parse_values`. It is a second copy of the LR loop, generated from its own template, and it
  is checked against `parse` only by a test on the samples of `test/rustactions`. It could call
  the kernel, or be stated as `parse` followed by a fold over the trace.
- `token_value`, and through it every token value `parse_values` sees.
- `Stacks::recycle`, the one `unsafe` block.
- The loop of lexers with several modes, and lexers whose rules `enter` or `leave` a mode. The
  kernel and the proofs are for one mode.

User code that nothing relates to its Lean counterpart:

- The Rust actions against the Lean actions. This is by design (D17): the theorems are about the
  parse tree, and the values are the user's.
- The Rust functions of the lexer (`rust f => path`, and `lexrt::to_nat`, `to_int`, `length`)
  against their Lean definitions. For `g s` rules this is also the terminal, which the theorems
  trust. For the built-in functions the difference is known (fixed width, `None` on bad input);
  for user functions such as `keyword_or_identifier` it is not checked at all.

Coverage and maintenance:

- Only Cedar has a proof package (`test/cedar/rust_bridge`). `CedarSchema.lig` has `gen_rust`
  and a one-mode lexer but no `gen_rust_verif`; `rustactions.lig` and `rustarena.lig` have
  neither. No public grammar without a lexer has a package, so the parser-only path of the
  generator is not exercised in this repository.
- A stale package is not detected. `lake build parsers` passes `--skip-rust-verif`, so a change
  to the tables or to `generated.rs` does not regenerate `rust_bridge/`, and CI builds neither
  `rust/verif` nor any bridge. Only a manual run of `leanparsergenerator` with Charon and Aeneas,
  then `lake build` in the package, shows that the proof still holds.
- A change to `rust/lpg-kernel` needs `--rust-extract-kernel` and a manual update of the proofs
  in `rust/verif`.
- `lpg_kernel` is a path dependency, not a published crate, and the verifier finds `rust/verif`
  relative to it. A grammar outside this repository has to point at a checkout of it.
- The lexer check grows with the number of DFA states. It is split in blocks of 32 states to
  bound memory, and a lexer with a few hundred states still takes minutes and several GB.

Generation features that are not there:

- A translation of Lean actions to Rust (D4, D8, D9). `--rust-report` ("The action classifier")
  measures how much of a grammar's actions is plain data construction.
- Lexer actions outside the five forms, and compositions of functions in one action.
- Token payload types other than those in "Token types", and unbounded `Nat`/`Int`.
- A Rust header inside the `.lig`; the Rust functions live in the user's modules.
- The set of expected terminals at a parse error, which the Lean `diagnose` computes.
- A pull-based lexer (no token vector) and collapsing chains of unit productions, which
  dominate the 1600 nodes per Cedar file.

## Performance

Cedar corpus, 28 files, 49,670 bytes, one thread, per file, `cargo build --release` with LTO.
Lean is `cedar-bench` on the same machine and builds the AST:

| | Rust trace | Rust values | Lean |
|---|---|---|---|
| lex + parse | 14.2 µs | 33 µs | 88 µs |
| lex only | 3.4 µs | 3.4 µs | 44 µs |
| parse only | 11.0 µs | 29.3 µs | 43.7 µs |

"Rust values" is `parse_values` with the Rust actions of `test/cedar/cedar.lig`, which build the
CST of `test/cedar/rust/src/cst.rs` (a copy of the layered Cedar CST of `CedarAst.lean`, with
lists as `VecDeque`s and owned strings: about a dozen nested boxes per primary expression) and
drop it after each parse. The trace parser records a node per reduction and does no allocation,
so it is not the same work as the other two. Rust lex + parse is about 120 MB/s and the lexer
alone about 520 MB/s. The corpus is small and repeated, so the branch predictor learns it; a
larger and more varied input will be slower.

Allocating the token and node buffers on every call costs about 1.8 µs. Replacing every table
index in the hot loops with `get_unchecked` made no measurable difference, so bounds checks are
not a cost here and the generated code stays safe.

In `parse_values`, the LR loop costs about what the trace parser costs. Under `perf`, `malloc`
and `free` take about a fifth of the time, and `parse_values` itself (with the actions inlined)
about a third. On a grammar with a large, deep AST, an arena (`rust_ctx`) and a flat operand list
roughly halved `parse_values`, to within about 15% of the trace parser.

### Lexer optimization

Lex only on Cedar, per file, each step on top of the previous one (the token streams were
compared with the Lean lexer after each):

| Step | Lex only |
|---|---|
| first version: class-compressed table, state number times classes, accept array | 7.4 µs |
| states renumbered, a state is the offset of its row, accepting rows last (D16) | 6.0 µs |
| inner loop over self-loops (identifier characters, spaces) | 4.8 µs |
| `String` payloads are slices of the source, not owned (D13) | 3.4 µs |
| kernel `lex`, a state is its row number (D29) | 3.0 to 3.3 µs |

Tried and dropped: a separate "accepting and final" state range that stops the scan without
another load (no change). Scanning without building tokens took 4.0 µs of the 4.8, so token
construction was not the bottleneck until the allocations went; with the allocations gone the
loop is bound by the latency of the dependent table load (4.2 instructions per cycle, 0.3%
branch misses on this corpus). Going further would need a different scanner, for example two
bytes per step.

### C99

The C99 fixture has no lexer, so I tokenized three C programs with a throwaway Python lexer (it
tracks `typedef` names, so `TYPEDEF_NAME` is produced as the grammar expects). The fixture
grammar has no brace initializers and no declarations in `for` headers, so the programs avoid
them. 14,611 tokens in total, the largest file 13.6k. Parse only, from the same tokens: Rust
192 µs per file against 634 µs for the Lean parser (3.3x, about 76 million tokens/s against 23).
The Lean parser builds the C99 CST and the Rust one a trace. The C99 tables have 305 states and
184 productions.

## When something goes wrong

| Message | Cause |
|---|---|
| `lexer action … is not one of: skip, Tok.T, Tok.T s, Tok.T (f s), g s` | the action has another form |
| `` `f` has no Rust counterpart; declare `rust f => path::to::fn` in the %lexer block `` | `f` is not built in and has no `rust` line |
| `the value must be the lexeme … or one function applied to it` | a composition inside `Tok.T (…)` |
| `` `Tok.T` carries a value but the action gives none `` (or the reverse) | the action does not match the `%token` declaration |
| `no Rust type for the token value type …` | the `%token <T>` type is not in "Token types" |
| `Rust actions must be given for every rule and alternative` | some rule has no `!!rust{type}` or some alternative no `!!rust{…}` action |
| ``Rust actions need the token payloads, which come from a `%lexer` block`` | a grammar with Rust actions, tokens with payloads and no `%lexer` |
| ``in `!!rust{…}`: unterminated '{…}' block`` | unbalanced braces in the Rust text |
| a rustc error inside an arm of `parse_values` | the Rust action; the comment above the arm names the rule and alternative |
| ``the `eof` action must be …`` | the `eof` clause is not the `%eof` token |
| `a lexer rule enters unknown mode` | a transition names a mode that does not exist |
| `unexpected character '.'` (or `/`) while reading the `.lig` with the bootstrap frontend | the `gen_rust` path starts with `.` or `/` |
| `the proofs cover lexers with one mode; this one has several` (or `… whose rules stay in their mode`) | `gen_rust_verif` on a grammar the proofs do not cover; add `%option rust_verif_optional` to skip the package |
| `` `%option gen_rust_verif` needs `charon` `` (or `aeneas`) | the tools are not on `PATH` or under `$AENEAS_DIR` |
| `the translation of the kernel at … is not the proved one` | `rust/lpg-kernel` changed; run `--rust-extract-kernel` and update the proofs |

## The action classifier

Before Rust actions were written by hand, the plan was to translate the Lean actions. The
classifier from that plan stays as a read-only report: for every parser alternative and lexer
rule it says whether the action is built only from constructors, variables, lists, tuples and a
few library functions. It does not emit anything. For a grammar author it answers how much of
the grammar's Lean actions is plain data construction, which is also how much a Rust action is a
transcription:
```
lake env .lake/build/bin/leanparsergenerator --rust-report [-v] grammar.lig
```
`lake env` is needed because the classifier imports the modules the `.lig` header imports (for
Cedar, `cedar.CedarAst`), which must be built. The report lists, per grammar, how many actions
are emittable, each action that is not and why, how many actions use each emission rule, which
actions use a variable more than once, and the result of the domain checks below.

Code, all under `LeanParserGenerator/Emit/Rust/`:

| File | Contents |
|---|---|
| `Action.lean` | `AExpr`, the subset of Lean terms that can be emitted, and its parser |
| `Ty.lean` | `Ty`, the subset of Lean types: applications, products, subtypes |
| `Resolve.lean` | `Resolver`: what a global name is (constructor, function, projection), from the Lean environment |
| `Rules.lean` | `knownFns`: library functions with a Rust counterpart; `builtinAliases` |
| `Classify.lean` | `Blocker` (why not), `Used` (which rule), `analyze` |
| `Domain.lean` | domain checks for partial known functions on lexer rules |
| `Report.lean` | the report |

An action is emittable if it is built from variables, literals, `()`, tuples, list literals,
`::`, `++`, `.1`/`.2`, constructors (including `some`/`none` and `.c` shorthand), structure
instances `{ f := e }`, structure projections and the functions in `Rules.knownFns`, with every
constructor fully applied. The whole list of rules is `Used` plus `knownFns`, and the whole list
of reasons for refusing is `Blocker`.

Result on the public grammars (emittable / total):

| Grammar | Parser | Lexer |
|---|---|---|
| Cedar policies | 135 / 143 | 31 / 33 |
| Cedar schema | 93 / 102 | 16 / 18 |
| Cedar entities | 42 / 53 | 13 / 15 |
| C99 | 180 / 183 | no lexer |
| IMP | 22 / 22 | no lexer |
| Calc | 4 / 7 | 6 / 6 |

What blocks the rest, in Cedar: four lambdas and two applications of a bound variable (the
grammar builds paths in continuation-passing style, `fun path => … tail (path ++ [next])`), and
two calls of helper functions defined in the AST module (`Cedar.Add.fromIdent`,
`Cedar.Expr.fromIdent`). The two lexer rules are calls of functions defined in the `.lig` header
(`keywordOrIdentifier`, `stripStringQuotes`). Arithmetic (`e + t` in Calc), `if`, `match`, type
ascriptions and `.getD` are not in the subset. A next tier would translate helper functions whose
bodies are themselves in the subset; that would cover the helper calls but not the lambdas.

### Domain checks

`String.toNat!` panics, and returns 0, on a string that is not all digits. The type of the action
is fine; the regex of the lexer rule allows lexemes the function is not defined on.
`Rules.knownFns` records the domain of each partial function as a regex, and `Domain.lean` checks
that the language of the lexer rule, after the string operations the action applies, is inside
it (D10). It understands the lexeme itself and `s.replace "c" ""` for a single character `c`
(deleting a character is a homomorphism on regexes). The inclusion test explores the derivatives
of both regexes together with `DFA.build?WithVecs`. Every other expression is reported as not
checked. The check is informative and not trusted.

On the public grammars all the `toNat!`/`toInt!` calls are proved. A grammar with `0x` hex
literals going through `toNat!` is reported `NOT SATISFIED` for that rule.

## Decisions

Each decision is recorded here so it can be changed. "Implemented" means the generator,
classifier or report does it today.

| ID | Decision | Status |
|---|---|---|
| D1 | Actions are parsed by our own parser for a subset of Lean (`Action.lean`), not by Lean's parser, which does not know the notation a header declares. Text outside the subset is a blocker. | Implemented |
| D2 | Names are resolved against the Lean environment built from the header's `import`s, under its `open`s. Names defined in the header text itself are not visible and are reported as such. | Implemented |
| D3 | `.c` and `⟨…⟩` get their type from the expected type: the nonterminal's declared type, then constructor field types, tuple, list and `Option` components. A polymorphic constructor field loses the expected type. | Implemented |
| D4 | An action is emitted only if it uses the rules above and `knownFns`. Lambdas are never emitted. | Applies to lexer actions and the classifier; for parser actions superseded by D17 |
| D5 | A variable used more than once is a note ("copy needed"), not a blocker. | Reported by the classifier; with D17 it is the user's concern |
| D6 | `List T` as a Rust cons-list rather than `Vec<T>`, because `x :: rest` on a `Vec` is a front insert. | Superseded by D17: the user picks the type (a `VecDeque` with `push_front` does it in O(1)) |
| D7 | `Nat` becomes `u64` and `Int` becomes `i64`. A value out of range is an error in the Rust code (D15), so the correspondence theorem reads: if the Rust lexer succeeds, so does Lean's, with the same tokens. | Implemented for lexer token values |
| D8 | The Rust AST types are generated from the Lean environment. | Tried and dropped, see D17 |
| D9 | Unemittable actions become methods of a generated trait the user implements. | Not done; D17 puts the Rust text in the `.lig` instead |
| D10 | A partial known function carries its domain as a regex, and the generator checks lexer-rule languages against it. | Implemented for lexer actions |
| D11 | A structure instance must name exactly the structure's fields. | Implemented |
| D12 | In a parser action a binder has the type declared for its symbol, `x_span` has type `Runtime.Span`, and in a lexer action the lexeme is a `String`. | Implemented |
| D13 | A `String` token payload is a slice of the source, `&'a str`, and `Tok<'a>` has a lifetime parameter (only if some token has such a payload). Owned `String`s cost 1.4 µs of 6.0 on Cedar lexing in allocation and more in copying the larger token. | Implemented |
| D14 | A lexer action has one of five forms (`skip`, `Tok.T`, `Tok.T s`, `Tok.T (f s)`, `g s`); a Lean function used in one has a Rust counterpart, built in or declared with `rust f => path` in the `%lexer` block. | Implemented |
| D15 | A numeral that does not fit `u64`/`i64`, or a string `toNat!` is not defined on, makes the Rust lexer fail (`Unrepresentable`) instead of saturating or returning 0. Rust counterparts of lexer functions return `Option`. | Implemented |
| D16 | The lexer tables are a re-encoding of the byte DFA: states renumbered with the accepting ones last, a state is the offset of its row, a step is one load. The generator checks the re-encoding against the byte DFA before it writes it. | Implemented; for one-mode lexers the offset became the row number (D29), and the proof package checks the tables against the Lean DFA |
| D17 | A parser action has a Rust counterpart written by the grammar author, `!!rust{ … }` after the Lean action, pasted verbatim into the reduction. The Rust type of a rule is `!!rust{type}` after its Lean type. The generator does not parse, translate or check the Rust. The parse-tree correspondence is independent of the values. | Implemented |
| D18 | Values live on one `Vec` per distinct Rust type; the production being reduced pops from the stacks of its right-hand side symbols. Rejected: one enum of all value types, which has the size of the largest AST node and was copied on every shift and reduction. With an AST whose nodes were up to 500 bytes, two thirds of the time went to `memmove`; per-type stacks and nodes of at most 64 bytes (larger fields behind a `Box`) cut the cost of building the AST per token by more than half. | Implemented |
| D19 | Rust actions are all or nothing: every rule needs a type and every alternative an action, or none has any. | Implemented |
| D20 | The `.lig` frontend reads `!!rust{…}` without a change to `lig.lig`: the bootstrap lexer keeps the Rust text inside the type or action token, and `assembleSurface` splits it off. The committed bootstrap parser is unchanged. | Implemented |
| D21 | Macro-generated rules get Rust text from the expansion when the grammar has Rust actions: lists are `VecDeque<T>`, options `Option<T>`, `T` the Rust type of the element, the payload type for a token. A user who wants another representation writes the list rule by hand. | Implemented |
| D22 | A reduction whose action is just the name of its only binder, with the symbol and the rule of the same Rust type, generates no code. | Implemented |
| D23 | `%option rust_ctx T` adds `ctx: &'a T` to `parse_values`, visible in the Rust actions, and `%option rust_list P` makes the macro rules build `P::List<'a, T>` with `P::nil/one/cons(ctx, …)`. On a large grammar it halved the time of `parse_values`: the allocator was most of the cost, and the tree is freed at once. Rejected: an arena inside the generated code (the AST types are the user's), a thread-local arena (the lifetime of the values would be a lie). | Implemented |
| D24 | With `rust_ctx`, `Stacks::recycle` empties the stacks and changes their lifetime (a `transmute` of empty vectors), so one set of buffers serves many arenas. It is the only `unsafe` in the generated parser. | Implemented |
| D25 | The loops of `parse` and `parse_values` keep the top state in a local instead of reloading it from the stack after each push; `Tok::term` is `#[inline(always)]`. Between 9% (trace) and 16% (values) of the parse time on a large grammar. | Implemented |
| D26 | The LR loop of `parse` is `lpg_kernel::parse`, the same for every grammar, with the tables as arguments; the generated `parse` is a call. | Implemented |
| D27 | A lexed token is `Token { rule, term, start, end }`, with no value. `token_value(rule, text)` rebuilds the `Tok` from the text of the span, and `parse_values` calls it for the tokens it shifts. Rejected: `Spanned<Tok>`, whose lifetime and payload Aeneas cannot translate in `&mut Vec`. Tokens are 12 bytes instead of 32 and the Cedar timings did not change. | Implemented |
| D28 | Tables are 2D with one constant per row, all `u16`. Same layout as the flat arrays. | Implemented |
| D29 | A one-mode lexer is `lpg_kernel::lex` with the tables as arguments. A state of `LEX_TRANS` is its row number, not the offset of its row (D16), because Aeneas elaborates one array literal in time superlinear in its length (4000 entries: 140 s), so the table has one constant per row. The Cedar lexer did not get slower (3.0 to 3.3 µs per file, before and after). The functions of the rules run in a pass after the loop, so that the kernel has no closure. | Implemented |
| D30 | The kernel's `parse` takes a step budget `fuel` (the generated parser passes `lpg_kernel::FUEL`, 2^62) and fails with `TERM_OUT_OF_FUEL` when it runs out, so that it is a total function without a termination proof from the tables. A reduction with no goto accepts whatever the production, as `Exec.reduce` does, so that the kernel computes `Exec` on every table. | Implemented |
| D31 | `%option gen_rust_verif <dir>` makes the generator write a grammar's proof package: it runs Charon and Aeneas on the crate (and on its kernel, which must translate to the proved `rust/verif/Kernel/`), and writes the certificate and the proofs from its own tables. The package requires `rust/verif` and shares its packages. `lake build parsers` passes `--skip-rust-verif`, so that the build does not need the tools. `%option rust_verif_optional` turns a grammar the proofs do not cover into a warning. Rejected: shell scripts around the tools, and parsing the generated Rust back (the generator has the tables). | Implemented |
