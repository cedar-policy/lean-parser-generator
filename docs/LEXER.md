# LEXER

The lexer produces the token type declared by `%tokentype`, with
regular-expression definitions, maximal-munch matching, mode stacks, `skip`, and
an optional `eof => TOKEN` action. It is generated by the offline CLI, parallel to
the parser:

A `%lexer { … }` block in the `.lig` file (§8) is read by `leanparsergenerator`,
which builds the DFA and the validator certificate at generation time
(`Lexer.DFA.build?WithVecs`, ordinary compiled code, like Pager construction) and
writes an inspectable `FooLexer.lean` module: the tokenizer with its DFA tables
and certificate as literal data (a `Lexer.Compiled Tok`), the `native_decide`
validation theorem `FooLexer.validated⟨m⟩`, the maximal-munch soundness corollary
`FooLexer.scanSound⟨m⟩`, the flat `state × class` tables (`FooLexer.cflat`) with
their `native_decide` agreement theorem `FooLexer.flatValidated⟨m⟩`, and a
`FooLexer.tokenize` entry point that runs the fast flat scanner and returns
`List (Runtime.Positioned Tok)` — each token wrapped with its source `Span`
(`Lexer.tokenizeFlatStrPos`, §9.7 step 1, §9.8) (`Emit/CodegenLexer.lean`). The
bare `List Tok` path stays available as `FooLexer.tokenizeBare`
(`Lexer.tokenizeFlatStr`), used by the roundtrip theorems and the byte path;
`tokenizeFlatStrPos_val` proves the positioned tokens' values are exactly the
bare output, so `tokenize_sound` transfers unchanged. This is the
analogue of the parser's generated
modules — untrusted construction plus emission, with the emitted `native_decide`
the checked boundary.

The DFA construction, scanner, validator, and soundness proofs live in `Lexer/`
and are shared by every generated lexer; only the tables and certificate differ
per grammar. An earlier in-Lean DSL that built the same tables at Lean
*elaboration time* has been removed: there is one path, the CLI, and generated
lexers are written source files, not spliced definitions. `Compiled.ofTokenizer`
(`Lexer/Engine.lean`) still builds the tables at run time, but only as the
cross-check reference used by `test/cedar/CedarBench.lean`, not as a generation
path.

A verified bytes-to-tokens layer is later work and can remain independent of the
parser refinement.

## Lexer Roundtrip

(This is planned work. This section is an intermediate design; the open questions
at the end are unresolved.)

The property we want is a printer/lexer inverse: the user supplies a way to
*print* tokens, and we prove that printing a token sequence and lexing the result
gives back the same sequence. It is not a text-identity round trip and it does not
hold for every token value. I state it as a token fixed point, restricted to the
tokens the lexer can actually produce.

### The statement holds on reachable tokens, not on all token values

The statement below is true for Cedar and is not vacuous. It is a fixed point on
*reachable* tokens:

```
∀ T, Reachable c T → tokenize c (render T) = .ok T
```

`render : List Tok → String` prints a token list; `Reachable c T` says the token
list `T` can be emitted by `tokenize c` on some input. I do not state the
unrestricted `∀ T` form, because it is false: `IDENTIFIER "if"` is a well-typed
`Tok`, but Cedar's lexer folds `"if"` to `.IF`, so no source lexes to
`[IDENTIFIER "if"]` and `render` of it re-lexes to `[IF]`. The unrestricted form
would ask us to prove something false, not merely something hard. Restricting to
reachable tokens excludes exactly the values the lexer never produces.

Note this compares *tokens*, not text. Most of the "lossy" cases in DESIGN.md §9.4
are only lossy against text identity and disappear under the fixed-point framing:
`.NUMBER 007` never arises (the action normalizes to `.NUMBER 7`), and `render`
emits the canonical `"7"`, which re-lexes to `.NUMBER 7`. The one case that would
break the fixed point — a folded keyword surfacing as an identifier — is excluded
by reachability, not patched around.

### Defining `Reachable` through the action makes it structural and excludes folded keywords

Define reachability per token, through the rule action:

```
ReachableTok c t := ∃ rule s, Regex.matchesFull (rules[rule]) s ∧ (acts[rule] s).emit = some t
```

A token is reachable when some rule matches some lexeme `s` and that rule's action
emits `t` on `s`. Defining it this way has two consequences.

First, it is structural. It ranges over rules and lexemes, so proofs induct over
the rule set rather than inverting an opaque `∃ s, tokenize c s = .ok T`
existential whose witness `s` is unrelated to `render T`.

Second, it bakes in the keyword exclusion. Cedar's identifier action is
`keywordOrIdentifier value`, which emits `IDENTIFIER value` only when `value` is
not a keyword. So `ReachableTok c (IDENTIFIER v)` already carries `v ∉ keywords`.
The exclusion of `IDENTIFIER "if"` falls out of the action; it is not a separate
side condition we have to state.

For a single-mode lexer whose actions all `stay`, a token *list* is reachable iff
every element is a `ReachableTok`: the run concatenates independent maximal-munch
steps, so any sequence of reachable tokens is itself reachable. Multi-mode lexers
(`push`/`pop`) add an ordering constraint on the list; I defer that.

### Coverage rules out a vacuous reachability precondition

Reachability is a precondition, so on its own the round-trip theorem could hold
trivially if few tokens were reachable. To rule that out, state a coverage
property as part of well-formedness:

```
∀ (k : constructor of Tok), ∃ v, ReachableTok c (k v)
```

Every declared token constructor is producible by the lexer — no dead token. This
is logically independent of round-trip (it is the "no unreachable rule" idea in
the well-formedness section above, stated on tokens rather than rules), and it is
what reassures us the reachability precondition is not quietly vacuous. It is not
what makes round-trip go through.

### The witness-synthesis problem for value-token coverage

Coverage over a *constant* token is easy: the token's rule matches a fixed literal
string, so the generator prints that literal and closes
`tokenize (lit ++ sep) = .ok [K, EOF]` by `native_decide`. The reachability
witness is the literal itself.

Coverage over a *value-carrying* token `K : τ → Tok` is the statement
`∃ v : τ, ReachableTok (K v)` — *some* payload value is producible. To prove it we
must exhibit one source string `s` such that `tokenize s` yields a token list whose
head is `K v` for some `v`. That is a **witness-synthesis** problem: find an input
lexeme that the *whole lexer* maps to the constructor `K`. It is harder than the
constant case for three independent reasons, and only the first is about the regex.

1. **Maximal munch and rule competition.** The lexeme must not only match `K`'s
   rule; it must *win* maximal munch against every other rule on that input. A bare
   digit `0` matches a `MIXED` rule (`digit idcont*`), but an earlier `NAT`
   rule matches the same length and wins the tie, so `0` lexes to `NAT`, not
   `MIXED`. A correct `MIXED` witness needs a trailing non-digit (`0a`) so it is
   strictly longer than any `NAT` prefix. The generator can decide this by
   simulating munch (`Lexer.bestMatch` over the mode's regexes): enumerate candidate
   lexemes from `K`'s rule regex and keep one whose `bestMatch` winner is exactly
   `K`'s rule, consuming exactly the candidate. This part is mechanical and is what
   the current generator does.

2. **The constructor is chosen by the action, not the rule.** The rule's *emit
   expression* need not name `K` syntactically. Cedar's identifier rule is
   `identStart identCont* as value => { keywordOrIdentifier value }`. The action
   `keywordOrIdentifier` returns `.IDENTIFIER ⟨value, _⟩` when `value` is not a
   keyword and a keyword token otherwise. So `IDENTIFIER` is reachable (`a` is not a
   keyword) but the generator cannot see this by scanning the emit string for
   `Tok.IDENTIFIER`: the mapping from lexeme to constructor runs through arbitrary
   user Lean the generator does not evaluate. Any purely syntactic "does the emit
   mention `K`" test misses folded-identifier tokens, and they are silently dropped
   from coverage — the failure we actually observe on cedar/cedarschema/cedarentities
   `IDENTIFIER`.

3. **The payload type may not be `Inhabited`, and its value is not known.** Even
   once a winning lexeme is found, the generator does not know the value `v` the
   action computes (it is `keywordOrIdentifier`'s output, or `String.toInt!`'s, …).
   The proof term must therefore *extract* `v` and the tail from the concrete
   `tokenize` result rather than name them. A naive extraction with a total `match`
   needs a fallback value (`_ => default`), which forces `Inhabited τ`. Cedar's
   `IDENTIFIER` payload is `{ s : String // s ∉ keywords }`, which has no `Inhabited`
   instance, so the fallback does not elaborate. An `Inhabited`-free extraction is
   needed: destructure the concrete result, build the witness in the reachable
   branch, and refute the other branches by evaluation.

The clean statement of the problem: **given a token constructor `K`, synthesize a
source string `s` and a Lean proof term of `∃ v, ReachableTok (K v)`, where the
generator can simulate the DFA/munch (it has the tables) but cannot evaluate the
rule action (opaque user Lean).** Point 1 is solvable by munch simulation; points 2
and 3 are the open part. A future robust solution may need to actually *run* the
compiled lexer+action on candidate lexemes (e.g. link the generated lexer and probe
it), or synthesize witnesses by other means (an SMT model of the rule regexes plus a
declared or inferred action post-condition). Until then the generator uses munch
simulation for the syntactically-visible constructors and falls back to a
per-grammar witness table for the folded cases, and coverage is stated over exactly
the tokens for which a witness was produced (with the un-witnessed ones named
explicitly, so the gap is visible rather than silent).

### Printers attach per token; value-carrying tokens carry an inversion proof

Printers are per-token, attached at the `%token` declaration. Valueless tokens
print a constant:

```
%token PLUS { "+" }
```

For a token whose rule is a string literal (`"+" => { Tok.PLUS }`), the generator
can infer the constant `"+"` from the rule, so `%token PLUS { "+" }` is usually
inferred and only the value-carrying tokens need writing. `skip` tokens have no
printer: they are absent from `T` by construction and are out of scope.

A value-carrying token needs a printer and a proof that the printer inverts the
rule's action. Under `roundtrips` the rule's action must be a **named payload
parser**, not an inline expression, so the inversion proof has something to name.
So calc's `digit+ as s => { Tok.NUM (String.toInt! s) }` becomes a rule that calls
a named `parseNum`, and the user supplies `parseNum`, a printer `printNum`, and a
lemma relating them, in `%lexerheader { … }` (or the imported `Ast.lean` — both are
in scope in the generated lexer module):

```
%lexerheader {
  def parseNum (s : String) : Int := s.toInt!
  def printNum (n : Int) : String := toString n

  theorem printNum_inv (n : Int) : parseNum (printNum n) = n := by
    -- user's proof that parse ∘ print = id on Int
    sorry
}
%token <Int> NUM { print := printNum, inv := printNum_inv }
```

The `%token` annotation is keyed, not positional: `print :=` names the printer,
`inv :=` names the inversion lemma. The generator reads both names, emits `printNum`
into `render`, and cites `printNum_inv` in the generated per-token obligation. The
names resolve in the generated module because `%lexerheader` is copied there.

The inversion the user proves is the small statement in their own vocabulary,
`parse (print v) = v`, about their two functions only. It mentions neither
`tokenize` nor the separator. The generator emits the other half as a goal for the
user to finish: that `print v` matches the rule's regex and lexes maximally against
the trailing space (open question 1). Both the user's `inv` and the generated goals
are combined in the emitted round-trip theorem. A wrong printer or a false `inv`
cannot produce a round-trip theorem: the user cannot close `printNum_inv` or the
generated goal, so no theorem is emitted rather than a false one.

For Cedar's `STRINGLIT`, the action is `stripStringQuotes`, so the parser is
`stripStringQuotes`, the printer must re-add the quotes and re-escape, and the
lemma is `stripStringQuotes (printStr s) = s`. That lemma is provable only for `s`
in the string rule's payload set (no unescaped quote); see open question 4.

### The round-trip theorems go in a separate `FooLexerRoundtrip.lean`

The generated lexer stays as `FooLexer.lean` (tables, certificate, `tokenize`) and
does not change. The round-trip statements, the coverage statement, and the per-token
goals the user has to finish are emitted into a separate `FooLexerRoundtrip.lean`,
which imports `FooLexer`. Two reasons to split the file:

- `FooLexer.lean` compiles with no user obligations; a project that does not ask for
  round-trip never sees a `sorry`. The obligations exist only when `roundtrips` is
  requested, and only in the extra file.
- The user finishes the generated maximality goals in this file, and it cites the
  user's `inv` lemma (defined in `%lexerheader` or `Ast.lean`). Keeping the goals
  here separates the generated output the user is expected to touch from the parts
  that must not be hand-edited (`FooLexer.lean`, `FooParser.lean`,
  `FooVerified.lean`).

`render` is generated: it is assembled from the per-token printers and the space
separator, and it is emitted into `FooLexerRoundtrip.lean` alongside the theorems
about it. The user's own definitions — `printNum`, `parseNum`, and the `inv` lemma
— live in `%lexerheader` or `Ast.lean`. So the roundtrip file holds the generated
`render` and the theorems; the user writes only the printer, parser, and inversion
lemma in their own Lean, and finishes the emitted goals in the roundtrip file.

`render` inserts a separator between every pair of rendered tokens (always insert,
not conditional — it is simple to prove and needs no analysis of which adjacencies
would mis-lex). For now the separator is the single space `" "`, and the round-trip
theorem takes as a hypothesis that the lexer has a `skip` rule matching `" "`.
Inferring the separator from the `skip` rules is deferred (open question 5).

The properties are opt-in, gated by an annotation on the `%lexer` block:

```
%lexer {
  …
} [% sound, roundtrips, covers]
```

- `sound` — the maximal-munch soundness already proved (§Lexer Soundness).
- `covers` — the coverage property (every token constructor is producible).
- `roundtrips` — the reachable-token fixed point.

`roundtrips` requires `covers`: requesting `roundtrips` without `covers` is an
error, because without coverage the reachability precondition could be satisfied
by too few tokens to constrain anything.

### The proof splits into a per-token inverse, a list induction, and a separator lemma

- The per-token fixed point: for each reachable token, its rendering followed by a
  space lexes to that one token,
  `ReachableTok c t → tokenize c (renderTok t ++ " ") = .ok [t]`. For constant
  tokens this is a finite `native_decide` check over the constructors. For a
  value-carrying token `K` with parser `parseK`, printer `printK`, and user lemma
  `invK : ∀ v, parseK (printK v) = v`, the obligation splits in two: the generator
  proves `printK v` matches `K`'s rule regex and the trailing space makes the match
  maximal (so lexing runs `parseK` on exactly `printK v`), and `invK` supplies
  `parseK (printK v) = v`. Composing them gives `tokenize c (printK v ++ " ") = .ok [K v]`.
  The user proves `invK` and finishes the emitted regex-match goal, both in
  `FooLexerRoundtrip.lean`.
- The list induction: `render (t :: ts) = renderTok t ++ " " ++ render ts`. Given
  the per-token fixed point and a space that breaks maximal munch between adjacent
  tokens, the list folds by induction on `T`.
- The separator lemma: the space re-lexes to nothing (it is consumed by the
  assumed `" "` `skip` rule) and does not merge with an adjacent rendered token
  under maximal munch. I have not checked that this composes across the token
  boundary; it is what makes the list induction sound, and it depends on the
  maximal-munch machinery in §Lexer Soundness.

No new proof infrastructure beyond `Lexer/Validator.lean`'s `matchesFull` /
`longestMatch` machinery is obviously required, but I have not checked that those
lemmas compose across the separator boundary.

### What is proved so far

Two layers are in place: a hand-written, lexer-independent proof library, and a
**generated** per-lexer roundtrip module.

The library `LeanParserGenerator/Lexer/Roundtrip.lean` (kernel-checked, axioms
`propext`/`Classical.choice`/`Quot.sound` only, no `native_decide`, no `sorry`):

- `scan_go_append` — **scan suffix stability**: `DFA.scan.go` stops at the first
  character with no matching edge, so once the walk over a prefix `xs` dies, scanning
  `xs ++ ys` equals scanning `xs`. This is the general fact that makes the separator
  break maximal munch independently of the rest of the input, and it reduces the
  per-token peel to a check that inspects only `renderTok t` and the separator
  character — a finite, suffix-independent, generatable check.
- `decidableDiesOn` / `diesOn_head` — `DiesOn` is decidable, and it inspects the
  suffix `ys` only through its first character, so a *variable* tail can be dropped.
  Together these let the peel's side condition be a finite `native_decide` check even
  though the rest of the input is a free variable.
- `scan_lit_sep_indep (dfa lit sepCh rest) (hdies : DiesOn dfa 0 lit [sepCh])
  : DFA.scan dfa (lit ++ sepCh :: rest) = DFA.scan dfa lit` — the packaged per-token
  scan peel: if the token lexeme `lit` dies as soon as it meets the separator
  character, its scan is independent of everything after the separator, for every
  `rest`. This is the resolution of open question 2 (scan composition across the
  separator boundary), reduced to one `native_decide` check on `DiesOn dfa 0 lit
  [sepCh]`.
- `peel_emit` / `peel_skip` — the two single-token loop steps, each proved for a
  *variable* suffix by composing `scan_lit_sep_indep` with
  `tokenizeAuxDFA_step_emit`/`_skip`. `peel_emit` peels an emitting token's lexeme;
  `peel_skip` drops the separator (`emit = none`) when it dies on the next rendered
  character. Composing them gives the full per-token `hpeel` (emit the token, skip
  the separator, land on the rendered suffix) — verified on calc, with all the
  per-token facts discharged by `native_decide` and only the suffix universally
  quantified. All of `decidableDiesOn`, `diesOn_head`, `scan_lit_sep_indep`,
  `peel_emit`, `peel_skip` are axiom-clean (only `propext`; no `sorry`, no
  `native_decide` axiom, no `Classical.choice`).
- `tokenizeAuxDFA_fuel_mono` — fuel monotonicity (a run that succeeds at `fuel`
  succeeds identically at any `fuel' ≥ fuel`), plus `tokenizeAuxDFA_nil_eq` and the
  single-step rewrites `tokenizeAuxDFA_step_emit`/`_skip`.
- `render`/`render_nil`/`render_cons` and `tokenize_render_fold` — the general list
  roundtrip by induction on the token list, from a per-token peel hypothesis.

The generated module, one `FooLexerRoundtrip.lean` emitted beside each lexer by the
generator (`Emit/CodegenLexer.lean`'s `generateRoundtripFrom`, run by the `parsers`
Lake target after the lexer):

- A generated `renderTok`/`render`. `renderTok` is **inferred from the grammar**:
  `regexLiteral?` reads the literal string each valueless token's rule matches (a
  `cat` chain of single-character classes), so `PLUS` printing `"+"` comes from the
  `"+"` rule. Value-carrying tokens print the empty string (out of scope; they need
  the user inversion lemma, open question 1).
- For each reachable constant token, the fixed point
  `tokenize (renderTok t ++ " ") = .ok [t, EOF]`, discharged by `native_decide`
  (same axiom budget as the lexer's own table certificate — the standard three plus
  one `native_decide` axiom). `tokenize` appends `EOF`; the separator is a single
  space, consumed by the whitespace `skip` rule. Generated counts: calc 5,
  CedarSchema 15, Cedar 29.

Cedar shows the design's keyword-folding and reachability points concretely: the
folded keywords (`if`, `permit`, …) are reachable and get generated theorems, while
`IDENTIFIER` — now typed `{ s : String // s ∉ keywords }` in the grammar — is a
value token, so it is excluded from `render` automatically and an identifier holding
a keyword is not just unreachable but unrepresentable.

What remains open toward the full generated `∀ reachable T,
tokenize (render T) = .ok (T ++ [EOF])`: the connective work wiring `scan_go_append`
and the per-token peel into `tokenize_render_fold` (mechanical, in progress), and the
value-token inversion lemma (open question 1). The suffix-generic obstacle that
blocked the old approach (open question 2) is resolved by `scan_go_append`.

The generated module is hole-free: it emits `render_roundtrip_all` (the list of all
constant tokens, `native_decide`), the per-token fixed points, `coverage`, and a
`#eval guarantees` summary. It no longer states the `∀ s` `render_roundtrip_general`
theorem: that was the one place needing a `sorry` (the unproved step is the
`tokenizeBare` flat runtime → `tokenizeAuxDFA` bridge), and a module that always carries
a `sorry` is worse than one that states the sublanguage it actually proves. The library
route for the general statement (`tokenize_render_fold` + `peel_emit`/`peel_skip` +
`scan_lit_sep_indep`) stays in `Lexer/Roundtrip.lean` for when the bridge is done.

### Parser roundtrip (token-generation inverse) and the full roundtrip

The parser roundtrip is token-level, the clean inverse of `parse`: the user supplies
`unparse : StartTy → List Tok` and the generated `FooParserRoundtrip.lean` proves
`parse (unparse t) = some t` for the ASTs in a `corpus`. It is opt-in via
`%option roundtrip_parser <unparse>` (DESIGN §16.5). The module is hole-free: it states
the roundtrip over the user's `corpus` (`roundtrip_corpus`, `native_decide`), not a
universal `∀ t` (which would invert the LR automaton and is false for a partial
`unparse`), and emits a `#eval guarantees` summary. The corpus lives in the user's
`<Base>Unparse` module, so adding an AST there — the whole specification — survives
regeneration.

`%option roundtrip_format <renderTok>` names a complete token renderer and adds the
*formatter idempotence* lemma — formatting the token stream with a space, newline, or
tab all re-lex to the same tokens — and the *full* AST↔source roundtrip, the
composition of the token-level parser roundtrip with the lexer roundtrip. Both are
hole-free over the corpus. The conditions are that `renderTok` is complete and the
separator is whitespace the lexer skips, which is the lexer roundtrip's reachability
condition one level up.
`test/cedar/ParserRoundtripTest.lean` and `test/cedarschema/ParserRoundtripTest.lean`
show all three slices are non-vacuous on concrete `Policies`/`Schema` CST witnesses.

   `printK v` matches `K`'s rule regex and the trailing space makes the match
   maximal — is emitted for the user to finish, because `printK` is a user function
   whose outputs the generator cannot enumerate. What should the emitted goal say?

1. The user proves `invK : ∀ v, parseK (printK v) = v`. The other `∀ v` goal —
   `printK v` matches `K`'s rule regex and the trailing space makes the match
   maximal — is emitted for the user to finish, because `printK` is a user function
   whose outputs the generator cannot enumerate. What should the emitted goal say?
   A candidate is one membership fact, that every character of `printK v` is in the
   rule's leading character class, from which the generator derives maximality. Is
   that one fact enough, or does maximality need more?
2. Does the maximal-munch machinery in `Lexer/Validator.lean` compose across
   `renderTok t ++ " " ++ renderTok t'` to give "the space is skipped and the
   boundary does not merge"? If not, what lemma is missing?
3. For `push`/`pop` lexers, a reachable token list is constrained by the mode
   stack, not just elementwise. Defer, or state the ordering constraint now?
4. Proving the user's `STRINGLIT` printer is a right inverse needs `printStr s` to
   match the string rule's regex, which is a fact about the reachable payload `s`
   (no unescaped quote, etc.). Does that fact come from `ReachableTok` (through the
   action, as with keywords) or as a separate lemma?
5. Inferring the separator from a `skip` rule instead of fixing it to `" "`. What
   exactly do we check — that some `skip` rule matches a chosen single character —
   and what is the error when it fails?
