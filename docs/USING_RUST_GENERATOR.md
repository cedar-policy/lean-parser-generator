# Using the Rust generator

The Rust backend turns a `.lig` grammar into one Rust source file with a lexer and an
LR(1) parser. It uses the same Pager tables and lexer DFAs as the Lean backends. This
document says how to run it, what the generated file contains, and how to call it. The
design and the decisions behind it are in [RUST_PARSER.md](RUST_PARSER.md).

Status: prototype. The generated parser returns a trace of the parse (which tokens were
shifted and which productions were reduced), not an AST, because semantic actions are
not emitted yet. Nothing is proved about the Rust code. On the Cedar corpus the output
agrees with the Lean lexer and parser (see "Checking against Lean").

## Quick start

Build the generator and run it on the Cedar grammar:

    lake build leanparsergenerator
    .lake/build/bin/leanparsergenerator --backend rust test/cedar/cedar.lig /tmp/cedar.rs

That writes `/tmp/cedar.rs`. The Cedar grammar names its Rust file itself, so the
usual build also writes it:

    lake build parsers        # writes test/cedar/rust/src/generated.rs among the Lean modules

Then use it from the crate in `test/cedar/rust`:

    cd test/cedar/rust
    cargo build --release
    ./target/release/tree policy.cedar           # the parse tree as an outline
    ./target/release/check policy.cedar          # ok, lex, or parse <token> <state> <lookahead>
    ./target/release/cedar-rust-parser a.cedar b.cedar    # benchmark over files

## Asking for the Rust file in the `.lig`

Add an option to the directives, before `%%`:

    %option gen_rust rust/src/generated.rs

The path is relative to the directory of the `.lig`. It must start with a name, not with
`.` or `/`. With the option, `leanparsergenerator grammar.lig` (what `lake build
parsers` runs for the fixtures) writes the Rust file next to the Lean modules, creating
directories as needed, and prints `wrote …/generated.rs (Rust)`. To have the build
regenerate it when stale, list it in the `outputs` of the grammar's entry in
`genTargets` in `lakefile.lean`.

The first lines of the generated file say which `.lig` it came from:

    // Generated by LeanParserGenerator from a .lig grammar. DO NOT EDIT.
    // Source: test/cedar/cedar.lig

Without the option, `--backend rust <grammar.lig> <out.rs>` writes the file where you
say. Either way the Lean modules are unaffected: the `.lig` is parsed once, and the
Lean backends ignore the Rust-only parts described below.

Where the files of a grammar are named:

| File | Named by |
|---|---|
| Lean modules (`FooParser.lean`, `FooLexer.lean`, …) | the `.lig` file name and its `%option`s, in the same directory |
| the generated Rust file | `%option gen_rust` |
| the Rust functions that lexer actions call | `rust f => crate::module::f` lines in the `%lexer` block; the file is the handwritten Rust module of that path |

## What the generated file contains

All items are in the one file, which you include as a module (`mod generated;` or `pub
mod generated;`). It has no dependencies beyond `std`.

Common items:

- `EOF: u16`, the terminal index of the end-of-input token.
- `trait Terminal { fn term(&self) -> u16; }`, the terminal index of a token.
- `struct Spanned<T> { tok: T, start: u32, end: u32 }`, a token with its byte span.
- `mod term`, one `u16` constant per `%token`, named like the token.
- `NUM_TERMINALS`, `NUM_NONTERMINALS`, `NUM_PRODUCTIONS`, `NUM_STATES`.
- `term_name(t: u16)`, `nonterm_name(n: usize)`, `prod_lhs(p: usize)`, `prod_len(p:
  usize)`: names and shapes, for printing and for rebuilding the tree.

From the lexer, if the grammar has a `%lexer` block:

- `enum Tok<'a>`, one variant per `%token`, with a payload for the tokens that carry a
  value. A `String` payload is a `&'a str` into the source. The lifetime parameter is
  there only if some token has such a payload.
- `fn tokenize<'a>(src: &'a str, out: &mut Vec<Spanned<Tok<'a>>>) -> Result<(), LexError>`.
- `struct LexError { pos, byte_pos, ch, reason }` and `enum LexErrorReason`.
- `mod lexrt`, the Rust versions of the library functions that lexer actions may call.

From the parser:

- `fn parse<T: Terminal>(tokens: &[Spanned<T>], stack: &mut Vec<Entry>, nodes: &mut
  Vec<Node>) -> Result<(), ParseError>`.
- `struct Node { kind: u16, start: u32, end: u32 }`, `const PROD_FLAG: u16 = 0x8000`.
- `struct Entry`, the parse stack cell. It is public so the caller can own the buffer.
- `struct ParseError { token: usize, state: usize, term: u16 }`.

For a grammar without a `%lexer` block there is no `Tok`, `tokenize` or `lexrt`, and
the file has `struct Kind(pub u16)`, a token that is only a terminal index, which
implements `Terminal`.

## Calling it

A crate that uses the generated file, from `test/cedar/rust/src/lib.rs`:

    pub mod generated;
    pub mod hooks;     // the handwritten functions named in the %lexer block

    use generated::{Entry, LexError, Node, ParseError, Spanned, Tok};

    #[derive(Default)]
    pub struct Parser {
        pub stack: Vec<Entry>,
        pub nodes: Vec<Node>,
    }

    impl Parser {
        pub fn parse<'a>(
            &mut self,
            src: &'a str,
            tokens: &mut Vec<Spanned<Tok<'a>>>,
        ) -> Result<(), Error> {
            tokens.clear();
            generated::tokenize(src, tokens).map_err(Error::Lex)?;
            generated::parse(tokens, &mut self.stack, &mut self.nodes).map_err(Error::Parse)
        }
    }

`Cargo.toml` needs no dependencies. Build with `--release`; the numbers below are for
`opt-level = 3`, `lto = true`, `codegen-units = 1`.

`tokenize` appends to `out` and does not clear it. The last token it appends is the
`%eof` token. `parse` clears `stack` and `nodes` first, so keep the buffers between
calls to avoid allocating per parse (fresh buffers per call cost about 2 µs on Cedar).
If `tokens` has no end-of-input token, `parse` supplies one.

The tokens borrow the source, so the token vector belongs to the caller and lives as
long as the source. One vector can be reused over several sources if they all outlive
it, as in a loop over a list of files; otherwise make a vector per source.

### The lexer

`tokenize` is the longest-match loop: it runs the byte DFA from the current position
until it dies, remembers the last accepting state, and takes that rule. A tie between
rules goes to the earlier rule, as in Lean. It stops with an error if no rule matches or
the longest match is empty.

`LexError` fields:

- `pos`: the error position in characters, as in Lean's `LexError.pos`.
- `byte_pos`: the same position in bytes. Token spans are byte offsets too.
- `ch`: the offending character; `None` at end of input.
- `reason`: `NoMatch` (no rule matches), `Unrepresentable` (a rule matches but its value
  does not fit the Rust type, such as a numeral beyond `u64`), or `EndInMode` (end of
  input inside a nested lexer mode).

### The parse trace

On success `nodes` holds the tree in postorder: one node per shifted token, one per
reduction. The last node is the augmented start production `S' → S $`. A node's `kind`
is either a terminal index (a token) or `PROD_FLAG | p` for production `p`. `start` and
`end` are byte offsets; a node for an empty production has `start == end`.

To rebuild the tree, scan `nodes` with a stack: push a leaf for a token node, and for a
production node pop `prod_len(p)` subtrees and make them its children. The Cedar crate
has this as `src/bin/tree.rs`:

    fn build(nodes: &[Node]) -> Vec<Tree> {
        let mut stack: Vec<Tree> = Vec::new();
        for &node in nodes {
            let children = if node.kind & PROD_FLAG != 0 {
                let n = prod_len((node.kind & !PROD_FLAG) as usize);
                stack.split_off(stack.len() - n)
            } else {
                Vec::new()
            };
            stack.push(Tree { node, children });
        }
        stack
    }

For `permit(principal, action, resource) when { 1 + 2 };` the tree starts

    S' [0..52]
      policies [0..51]
        list_policy [0..51]
          policy [0..51]
            list_annotation [0..0]
            any_ident [0..6]
              common_ident [0..6]
                PERMIT "permit"
            LPAREN "("
            …

Productions come from the grammar after macro expansion, so names like `list_policy`
are the expansions of `list(policy)`.

`ParseError`:

- `token`: the index in `tokens` of the offending token.
- `state`: the LR state; `term`: the terminal index of the lookahead.
- `term == u16::MAX` means an internal inconsistency in the tables (a stack underflow, or
  a reduction with no goto that is not the augmented production). The tables come from
  a Pager construction that the Lean side validates, so this is not expected.

`term_name(term)` gives the lookahead's name. The set of terminals the state would have
accepted is not exposed; the Lean parser's `diagnose` computes it.

## Lexer rules the Rust backend accepts

The Lean backends accept any Lean term as a lexer action. The Rust backend accepts only
five forms, so that no Lean has to be translated. With `s` the `as` binder:

| Action | Meaning | Rust |
|---|---|---|
| `skip` | no token | |
| `Tok.IDENT` | a token without a value | `Tok::IDENT` |
| `Tok.NAME s` | the value is the lexeme; `NAME` carries `String` | `Tok::NAME(text)`, `text: &'a str` |
| `Tok.NAME (f s)` or `Tok.NAME s.f` | the value is `f` of the lexeme | `Tok::NAME(v)` for `Some(v) = f(text)` |
| `g s` | the token is `g` of the lexeme | the token `t` for `Some(t) = g(text)` |

Anything else is rejected, with the mode and rule number in the message. A composition
like `(s.replace "_" "").toNat!` is rejected; define one function for it.

### Functions in actions

`f` and `g` are Lean functions, and each needs a Rust counterpart. These have one
already, in the generated `lexrt` module:

| Lean | Rust |
|---|---|
| `String.toNat!` | `lexrt::to_nat(&str) -> Option<u64>` |
| `String.toInt!` | `lexrt::to_int(&str) -> Option<i64>` |
| `String.length` | `lexrt::length(&str) -> Option<u64>` |

For any other function, add a line to the `%lexer` block, before the rules, that names
the Rust function, and write it in a handwritten Rust module. From `cedar.lig`:

    %lexer {
      let identStart = ['a'-'z' 'A'-'Z' '_']
      …
      rust keywordOrIdentifier => crate::hooks::keyword_or_identifier
      rust stripStringQuotes   => crate::hooks::strip_string_quotes

      | identStart identCont* as value => { keywordOrIdentifier value }
      | "\"" … "\"" as value           => { Tok.STRINGLIT (stripStringQuotes value) }
      …
    }

and in `hooks.rs`:

    use crate::generated::Tok;

    pub fn keyword_or_identifier(text: &str) -> Option<Tok<'_>> {
        Some(match text {
            "permit" => Tok::PERMIT,
            "forbid" => Tok::FORBID,
            …
            _ => Tok::IDENTIFIER(text),
        })
    }

    pub fn strip_string_quotes(text: &str) -> Option<&str> {
        let mut cs = text.chars();
        cs.next();
        cs.next_back();
        Some(cs.as_str())
    }

The signatures are fixed:

- for `Tok.NAME (f s)`: `fn f(&str) -> Option<R>`, with `R` the Rust type of the value
  `NAME` carries (`&str` for a `String`; elided lifetimes tie it to the lexeme);
- for `g s`: `fn g(&str) -> Option<Tok<'_>>`.

`None` means "the Lean function has a result that Rust cannot represent here"; the lexer
then fails at the start of the lexeme with `Unrepresentable`. A function that is total
returns `Some` always.

The Lean definition of the function stays in the `%lexerheader` of the `.lig` and is the
specification. The two definitions are separate pieces of code and nothing yet checks
that they agree; that is the job of the verification step, and until then of the
differential test below. Where the types differ, the Rust one has fewer constraints:
Cedar's `IDENTIFIER` carries `{s // s ∉ keywords}` in Lean and a plain `&str` in Rust.

Keywords do not need a function. Because the lexer takes the longest match and breaks
ties by rule order, listing the keywords as rules before the identifier rule gives the
same tokens. That form needs no Rust code, and in a test on Cedar it produced identical
token kinds and spans.

### Modes

`rule name { … }` blocks with `enter m` (push) and `leave` (pop) are supported, with the
semantics of the Lean lexer: a stack of modes starting with the first, and end of input
is an error unless exactly one mode is on the stack.

### The `eof` action

If there is one, it must be the constant `Tok.<the %eof token>`. The Rust lexer always
appends the `%eof` token, also when the `.lig` has no `eof` clause; in that case the Lean
lexer's token list has no end token and the parser supplies it, so parse results agree.

## Token types

`Tok` has a variant per `%token`, with the name from the `.lig`. A token with a value
takes the Rust type of the declared Lean type:

| Lean type | Rust type |
|---|---|
| `String` | `&'a str`, a slice of the source |
| `Nat` | `u64` |
| `Int` | `i64` |
| `Bool` | `bool` |
| `Char` | `char` |
| `{ x : T // p }` | the Rust type of `T` (the predicate is dropped) |

Any other type is an error naming the type. `Tok` derives `Clone`, `Debug`, `PartialEq`
and `Eq`, and implements `Terminal`.

`Nat` and `Int` are fixed width. A numeral beyond the range is not saturated and not
wrapped: the built-in functions return `None` and the lexer reports `Unrepresentable`.
Lean accepts the same numeral with an unbounded `Nat`, so this is a difference; the Rust
lexer never returns a wrong value. The Cedar grammar assumes its numerals fit `u64`.
`lexrt::to_nat` also returns `None` on a string that is not all decimal digits, where
`String.toNat!` panics and returns 0.

## Grammars without a lexer

C99's fixture has no `%lexer` block, so the file has only the parser. Supply tokens
yourself, as `Spanned<Kind>`, using the constants in `mod term`:

    use generated::{parse, term, Kind, Spanned, EOF};

    let toks = vec![
        Spanned { tok: Kind(term::INT), start: 0, end: 3 },
        Spanned { tok: Kind(term::IDENTIFIER), start: 4, end: 5 },
        Spanned { tok: Kind(term::SEMICOLON), start: 5, end: 6 },
        Spanned { tok: Kind(EOF), start: 6, end: 6 },
    ];

or implement `Terminal` for your own token type and parse a `&[Spanned<YourTok>]`.

## Checking against Lean

Nothing proves the Rust code correct yet. What we do instead is compare it with the Lean
backends on mutated inputs. For Cedar, the recipe is:

1. Make inputs: take the corpus files and apply random edits (truncate, delete a range,
   insert a fragment, replace, duplicate), 3000 files. Many become errors, which is the
   point.
2. Lean side: a small program that, per file, runs `CedarLexer.tokenize` and
   `CedarParser.diagnose`, and prints `ok`, `lex`, or `parse <position> <state>
   <lookahead>`. For the lexer, print each token as `<terminal>:<start>-<end>` and its
   value.
3. Rust side: `check`, `check --tokens` and `check --values` print the same formats.
4. Diff.

On the Cedar corpus mutants there are no differences in acceptance, error position, LR
state, lookahead, token terminals, token spans or token values; a lexer with three modes
was checked the same way. The differences that are known are the ones listed under "Token
types" and the end-of-input token above. Before trusting a new grammar, run the same
comparison on it. The cases that matter most are functions you wrote twice (the Lean one
and the Rust one) and inputs with non-ASCII characters, where character and byte offsets
differ.

## Performance

Cedar corpus (28 files, 49,670 bytes), one thread, per file; Lean is the Lean parser
building the AST:

| | Rust | Lean |
|---|---|---|
| lex + parse | 15 µs | 88 µs |
| lex only | 3.4 µs | 44 µs |
| parse only | 11 µs | 43 µs |

The Rust parser does less per reduction (it records a node; Lean runs the semantic
action), so the numbers do not compare equal work. Lexing is about 520 MB/s. The corpus
is small and repeated, so the branch predictor learns it; a larger and more varied
input will be slower.

## When something goes wrong

| Message | Cause |
|---|---|
| `lexer action … is not one of: skip, Tok.T, Tok.T s, Tok.T (f s), g s` | the action has another form |
| `` `f` has no Rust counterpart; declare `rust f => path::to::fn` in the %lexer block `` | `f` is not built in and has no `rust` line |
| `the value must be the lexeme … or one function applied to it` | a composition inside `Tok.T (…)` |
| `` `Tok.T` carries a value but the action gives none `` (or the reverse) | the action does not match the `%token` declaration |
| `no Rust type for the token value type …` | the `%token <T>` type is not in the table above |
| `the `eof` action must be …` | the `eof` clause is not the `%eof` token |
| `a lexer rule enters unknown mode` | a transition names a mode that does not exist |
| `unexpected character '.'` (or `/`) while reading the `.lig` with the bootstrap frontend | the `gen_rust` path starts with `.` or `/` |

A Rust compile error in the generated file about a missing function means the path in a
`rust` line does not match your module; the generated code calls the path as written.

## What is not there

- Semantic actions and an AST. `leanparsergenerator --rust-report grammar.lig` (run under
  `lake env`) says which actions of a grammar could be emitted and why not for the rest;
  see RUST_PARSER.md.
- Proofs, and any statement of correctness beyond the differential tests.
- A Rust header inside the `.lig`; the Rust functions live in your own module.
